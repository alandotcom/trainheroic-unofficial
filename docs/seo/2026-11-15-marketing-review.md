## Crawler-access diagnosis

From one network origin, the following live tests were reproducible:

- curl with a normal curl UA: HTTP 200.
- curl with `Python-urllib/3.9`: HTTP 403, body `error code: 1010`.
- urllib with its default UA: HTTP 403 with the same error.
- urllib with curl's UA: HTTP 200.
- urllib with the descriptive `my-trainheroic-docs-client/1.0` UA: HTTP 200 for `llms.txt`.
- Requests identifying as `Googlebot`, `OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`,
  and `ChatGPT-User`: HTTP 200 on each of `/developers`, `/export`, and `/llms.txt`.

[Cloudflare's error 1010 documentation](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/)
describes browser-signature denial and library-default user agents. The controlled UA change
and matching error identify the observed problem as consistent with that behavior.
The zone's exact security setting was not inspected. These requests used simulated UA strings;
they do not establish access from verified crawler IPs or actual provider fetch infrastructure.
Google's access and selected canonical still need Search Console URL Inspection.

The robots file allows crawling, and the tested discovery UAs reached the content. No evidence
from this test justifies disabling security globally or treating a training-crawler policy as
a search-indexing policy. The application cannot repair an edge rejection with a robots change.

### Browser-export measurement

The static exporter currently sends no usage events. A sample download, button click,
non-empty file generation, and saved/opened file are different outcomes. Browser code can
observe successful file generation and initiation of a download; it cannot reliably prove
that a user saved or opened the file.

The initial measurement decision was audit and planning only. The user subsequently authorized
a new GA4 property and public-site integration. See [the GA4 setup](2026-11-15-ga4-setup.md)
for its consent boundary, identifiers, and events. New backend counters and actual export
completion tracking remain outside this pass. For a future implementation, the proposed event is
`export_download_started`, emitted only
after successful serialization and invocation of the browser download. Its payload should be
an allowlisted event name and format, with no identity, session token, dates, workout counts,
exercise names, filenames, referrer, or training contents. A sample-download event must be
separate from a real export. Document the retention, purpose, rate limiting, and collection
endpoint before enabling it. Aggregate counts alone will not identify unique converters.

For connections, continue using existing authorization and successful-tool counters. Define
an activated account separately if a later cohort analysis can establish its first successful
training action; neither an outbound connector link nor OAuth completion proves that outcome.
